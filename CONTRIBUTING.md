# Contributing to Rails CVE

Thanks for helping make Rails security notifications more useful. Small, focused contributions are welcome: clearer docs, receiver examples, accessibility improvements, and fixes to ingestion or delivery.

## Before you start

- For a bug, [open an issue](https://github.com/aviflombaum/rails-cve/issues/new/choose) with reproduction steps and expected behavior. Include versions and sanitized evidence.
- For a large feature, start with an issue describing the maintainer workflow and tradeoffs. Check the [roadmap](docs/plans/002-follow-up.md) first.
- For a vulnerability, follow [SECURITY.md](SECURITY.md). Do not disclose it in a public issue or PR.
- For upstream Rails vulnerability reports, use the [Rails security policy](https://github.com/rails/rails/security/policy), not this project's issue tracker.

## Local workflow

[Fork the repository](https://github.com/aviflombaum/rails-cve/fork), clone your fork, create a branch, and run:

```sh
bun install --frozen-lockfile
bun run setup
bun run db:local
bun run dev
```

Use Bun 1.3.14+ and Node 22+; CI uses Bun 1.3.14 and Node 24. No Cloudflare credentials are required. To load real public advisory data into local D1, call `http://localhost:8787/cdn-cgi/local/scheduled`. Tests mock all outbound requests and never contact subscriber endpoints.

Before opening a pull request:

```sh
bun run format
bun run check
bunx wrangler deploy --dry-run
```

`worker-configuration.d.ts` is generated by typecheck and is not committed. Production configuration belongs in ignored `wrangler.deploy.jsonc`; use the portable tracked `wrangler.jsonc` for local work and tests.

## Code and test expectations

- Keep changes focused and use strict TypeScript. Prefer the existing Hono, D1, and Web Crypto patterns.
- Preserve exact upstream version ranges. Don't guess whether a subscriber's application is affected.
- Keep signing secrets, account tokens, production data, private endpoint URLs, and receiver response bodies out of source, screenshots, and logs.
- Use prepared SQL statements and bounded request/response reads. Await asynchronous work or attach it to the Worker execution lifetime.
- Add regression coverage when changing authentication, tenant isolation, destination validation, signatures, deduplication, leases, or retries. Use the Workers runtime suite in `test/core.test.ts`.
- Visual changes should be checked on desktop and mobile, including keyboard access and empty/error states. Include screenshots in the PR.
- Add a numbered migration for schema changes. Describe effects on existing data, deployment order, and recovery. Do not change an already-deployed migration to retrofit a schema.
- Document event schema changes and keep examples consistent. A webhook contract change needs explicit compatibility discussion.
- Don't add automatic exploit execution, production access, merges, or deployments to investigation prompts. The maintainer remains in control.

Documentation-only changes do not need new tests. Run the checks relevant to your change and report what you verified honestly.

## Pull requests

Explain the concrete problem, resulting behavior, and validation. Link an issue when there is one. If a change alters operational limits, permissions, or user-visible behavior, call that out in the description and update the relevant guide.

Maintainers may ask for scope reductions or additional evidence. A proposal or PR is not a promise of acceptance or a support SLA.

## Community expectations

Read the [Code of Conduct](CODE_OF_CONDUCT.md).

Be kind, direct, and respectful. Critique ideas and code, not people. Harassment, discrimination, and disclosure of another person's private information are not welcome. Maintainers may remove inappropriate content or restrict participation. Report concerns privately to [dev@avi.nyc](mailto:dev@avi.nyc).
